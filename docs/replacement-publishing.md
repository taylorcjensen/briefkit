# Replacing a published brief

Publishing the same normalized title with the same publish API key replaces the static site at its existing URL. A freshly generated report in another directory behaves the same way. Removed assets are deleted, and the new duration and indexing settings take effect. There are no revision URLs or archived public pages. A failed upload leaves the previous working site in place. Response channels live separately and are not removed by replacement.

The server stores a SHA-256 fingerprint of the publishing API key in private `.briefkit.json` metadata, not the key itself. A different API key receives a distinct slug suffix; subsequent publishes with that key reuse its assigned URL. An API key cannot unpublish a brief owned by another key. **Rotating a key changes publisher identity**: keep the old key available for a final publish, or have the server operator migrate the fingerprint in the brief's private metadata. Do not transfer ownership merely by choosing the same title.

Pre-upgrade briefs with no stored publisher fingerprint cannot be claimed automatically: publishing to their base title returns HTTP 409 rather than overwriting or creating a duplicate. The server operator can explicitly migrate a legacy brief by adding `baseSlug` (the normalized title slug) and `publisherFingerprint` (SHA-256 hex digest of the intended API key) to that brief's `.briefkit.json` while the publish server is stopped. Back up the private metadata first and confirm the key's publisher before claiming it. Alternatively, remove the old brief deliberately with `briefkit unpublish` before publishing anew (the old URL then briefly disappears). For a rotated key, change only `publisherFingerprint` on that publisher's assigned brief after confirming the new key's identity; preserve `baseSlug` and `slug`. Do not copy API keys into metadata or logs.

Replacement stages the complete new site before changing the live directory. On a failed swap, the server restores the old directory. On restart after interruption, it restores the old directory if the new one was not installed, or removes the private rollback directory if it was. Publishing, unpublishing, and expiry cleanup of the same title serialize against a per-title filesystem lock; stale locks are cleaned on startup after the configured stale interval (`BRIEFKIT_INTERNAL_CLEANUP_STALE_MS`). If a publish reports a busy conflict, retry when the other operation completes.
